## 1. RINGKASAN EKSEKUTIF

- **87 fitur** diinventarisasi dari kode (bukan dari dokumen lama). 13 di antaranya **kode mati atau setengah jadi**.
- **Yang diuji secara nyata di browser:** alur pengguna penuh, transisi hall, panel info, panel pengaturan, 3 preset grafis, emulasi HP Android (portrait + landscape), dan 5 skenario kegagalan.
- **Temuan: 6 P0, 9 P1, 11 P2, 6 P3.**
- Empat P0 berakhir dengan **layar putih atau pengunjung terjebak permanen**: WebGL tidak didukung, `localStorage` rusak, jaringan putus saat loading, dan `webglcontextlost`.
- Satu P0 struktural: **gerak pemain tidak dibatasi per frame**, sehingga satu frame panjang (terukur 2,19 detik) memindahkan pemain **9,2 meter dalam satu langkah tabrakan** — di ruangan yang dalamnya 15 meter.
- Satu P0 pengalaman: **pengunjung yang berjalan lurus dari titik masuk melewati seluruh Hall 1 tanpa satu pun artefak masuk jangkauan**, lalu terlempar ke Hall 2. Perilaku default aplikasi adalah keluar dari pameran.
- **40,86 MB harus diunduh sebelum pengunjung bisa mulai** — sekitar 14 menit di jaringan Slow 3G.
- Mode VR hanya bisa ditinggalkan lewat tombol Start gamepad. Tanpa gamepad, satu-satunya jalan keluar adalah menutup atau me-refresh halaman.

> **Penilaian jujur: aplikasi ini belum layak dipakai banyak pengguna hari ini.** Fondasinya kuat dan sebagian besar fitur benar-benar berfungsi, tetapi setiap kegagalan yang pasti terjadi di pemakaian publik — GPU bermasalah, jaringan putus, data lama tersimpan — saat ini berakhir dengan layar kosong tanpa penjelasan, dan pengunjung yang tidak melakukan apa-apa selain berjalan lurus tidak akan pernah melihat satu artefak pun.

**Temuan baru yang muncul saat mengerjakan P2-3, tidak ada di laporan asli:**
`MiniArtifact` di `InfoPanel` punya `<Suspense>` tapi tidak punya error
boundary. `<Suspense>` hanya menangkap promise-nya, bukan penolakannya — jadi
satu `.glb` yang 404 melempar keluar dari `<Canvas>` panel, dan boundary
terdekat di atasnya adalah `AppErrorBoundary`. Satu model hilang mengubah
seluruh museum jadi layar kesalahan fatal begitu pengunjung menekan E di
artefak yang salah. Setara P0; sudah ditutup di `1c80e7e`.

**Tiga cacat lain yang ikut ditutup saat membangun E-6, juga tidak ada di
laporan asli:** menekan `E` dengan Pengaturan terbuka memfokuskan artefak di
balik dialog; `Escape` tidak pernah menutup Pengaturan; dan WASD terus berjalan
di balik dialog mana pun yang terbuka (dialog menelan mouse, tidak papan ketik).
Semuanya di `6e0e266`.

**Yang belum diuji ulang setelah semua perbaikan ini:** seluruh baris di bagian
8 masih berlaku. Perbaikan di atas diverifikasi lewat `lint` + `tsc` + `build`,
pembacaan kode, dan satu pemeriksaan Chrome headless terhadap build produksi
(`#root` terisi, `<canvas>` ada, onboarding tampil — jadi tidak ada layar putih
dari perubahan store). **Bukan** lewat pengujian runtime berulang seperti audit
aslinya.

**Catatan verifikasi (P3-4 & P3-5):** dua temuan ini adalah yang pertama di
laporan ini yang **benar-benar diuji berjalan di browser**, bukan hanya lewat
`lint`/`tsc`/`build` dan pembacaan kode. Ekstensi Chrome tetap tidak tersambung,
jadi pengujiannya lewat harness Chrome DevTools Protocol di luar repo yang
menjalankan **build produksi** (`vite preview`) dengan throttle jaringan, lalu
menekan tombol sungguhan dan membaca DOM hasilnya. Yang dibuktikan: gerbang
"Menyiapkan Galeri" benar-benar mengunci (ditekan saat 0% → onboarding tetap
terbuka), terbuka sendiri setelah muat selesai, dan menekan "Mulai Jelajahi"
sesudah itu benar-benar masuk museum (HUD muncul). Jalur gagalnya juga diuji
dengan memutus koneksi di tengah muat: tombol "Coba Lagi"/"Lanjutkan Saja"
terbukti bisa ditekan (uji `elementFromPoint`, bukan sekadar ada di DOM).

Satu cacat ikut ketemu lewat uji itu dan diperbaiki sekalian: kartu onboarding
memakai `transition-all`, dan `z-index` termasuk properti yang bisa
dianimasikan — jadi penurunan lapis 60 → 40 saat muat gagal ikut ter-*interpolasi*
selama 500 ms, dan selama itu tombol pemulihan tertutup kartu. Transisinya
dipersempit ke `transition-opacity`.

Yang secara spesifik **belum pernah disentuh di browser sungguhan:** panel
"Koleksi" dan alur "Kunjungi" (termasuk perpindahan antar hall) — ekstensi
browser tidak terhubung saat pengerjaan, dan `--dump-dom` tidak bisa melewati
onboarding. Aritmetika titik berdirinya diturunkan dan dibuktikan di pesan
commit, tapi itu bukan pengganti satu kali uji manual. Pengukuran ulang
kebocoran GPU, jeda frame, dan waktu muat juga sebaiknya dijalankan lagi sebelum
rilis publik.

### A.4 — Kebocoran memori & stabilitas

Diukur dengan membungkus `WebGLRenderingContext.create*/delete*` sebelum aplikasi dimuat, lalu membuka-menutup panel info **20 kali**.

```
heap JS                          : 212 MB -> 210 MB  (tidak tumbuh)
texture create/delete  sebelum   : 233 / 101
texture create/delete  sesudah   : 429 / 113
  -> 184 texture BOCOR dalam 20 siklus (±9 per buka-tutup)
buffer  create/delete  sebelum   : 2659 / 2180
buffer  create/delete  sesudah   : 3129 / 2260
  -> 390 buffer BOCOR dalam 20 siklus (±20 per buka-tutup)
program create/delete            : 100/37 -> 137/56
```

**Heap JS tidak tumbuh — dan justru itu yang berbahaya.** Kebocorannya ada di memori GPU, yang tidak terlihat di profiler JS sama sekali. Inilah mekanisme persis "aplikasi 3D makin lama makin berat lalu tiba-tiba mati" di HP: VRAM habis, driver mencabut context, layar hitam.

Penyebab yang teridentifikasi di kode:
1. `InfoPanel.tsx:43` membuat **`<Canvas>` kedua** (renderer WebGL kedua) setiap panel dibuka, dan `<Environment preset="city" />` di dalamnya memuat environment map baru tiap kali.
2. `MiniRealModel` melakukan `scene.clone(true)` — geometri dipakai bersama dua renderer berbeda.
3. `useEffect(() => () => ownedMaterials.forEach(m => m.dispose()))` hanya membersihkan material **kalau `materialOverride` diisi**; sebagian besar artefak tidak mengisinya, jadi tidak ada yang di-dispose.

Pemeriksaan khusus yang diminta prompt:

| Pola | Hasil |
|---|---|
| `material.clone()` tanpa `dispose()` | **Ditemukan** — `InfoPanel.tsx:221` & `ArtifactMesh.tsx` meng-clone material; dispose hanya berjalan di jalur `materialOverride` |
| `useGLTF` tanpa pembersihan | **Ditemukan** — tidak ada satu pun `useGLTF.clear()` di seluruh kode; cache model tumbuh sepanjang sesi |
| Listener tidak dilepas saat unmount | **Bersih** — semua `addEventListener` yang diperiksa punya `removeEventListener` pasangannya |
| Render target VR dibuat ulang tanpa `dispose()` | **Bersih** — `CardboardStereoView` men-dispose render target-nya |

## 5. DAFTAR TEMUAN

### P0 — Aplikasi tidak bisa dipakai / pengguna terjebak

---

**P0-1 — WebGL tidak tersedia → layar putih total**

- **Reproduksi:** buka aplikasi di perangkat/browser tanpa WebGL (atau dengan GPU di-blocklist Chrome, yang umum di HP Android murah).
- **Dampak:** `<div id="root">` benar-benar kosong. Bukan pesan, bukan logo — halaman putih. Pengunjung menyimpulkan situsnya rusak.
- **Penyebab:** `THREE.WebGLRenderer: Error creating WebGL context` dilempar di dalam `<Canvas>`; tidak ada error boundary di atasnya, jadi React melepas seluruh pohon komponen.
- **Bukti:** `{"text":"","canvas":0,"rootChildren":0,"blank":true}`
- **Usaha:** S (error boundary aplikasi + deteksi WebGL sebelum mount).

---

**P0-2 — `webglcontextlost` → layar hitam permanen**

- **Reproduksi:** `gl.getExtension('WEBGL_lose_context').loseContext()`, atau di dunia nyata: HP kelas bawah kehabisan VRAM, tab lama di latar belakang, driver GPU reset.
- **Dampak:** canvas mati permanen, HUD DOM masih melayang di atas kehampaan. Tidak ada `preventDefault()` sehingga context tidak pernah bisa dipulihkan browser, dan tidak ada `webglcontextrestored`.
- **Bukti:** `ctxLost: 21, ctxRestored: 0`; `THREE.WebGLRenderer: Context Lost.` ×20.
- **Usaha:** S–M.

---

**P0-3 — `localStorage` berisi nilai tidak valid → layar putih saat start**

- **Reproduksi:** set `museum-settings` ke `{"state":{"settings":{"graphicsQuality":"ultra"},...}}` lalu buka aplikasi.
- **Dampak:** `TypeError: Cannot read properties of undefined (reading 'shadowsEnabled')`. Aplikasi tidak pernah menyelesaikan render pertama. Pengunjung tidak punya cara tahu bahwa jawabannya adalah "hapus data situs".
- **Penyebab:** `merge` di `useMuseumStore.ts:337-351` hanya menyanitasi **tiga nilai optik VR**. Semua field lain — `graphicsQuality`, `deadzone`, `textSize`, `controlMode`, `cameraFOV` — masuk mentah dari disk. `GRAPHICS_PRESETS[quality]` lalu `undefined`.
- **Kenapa ini pasti terjadi:** setiap kali nama tier preset berubah, atau field settings dihapus, seluruh pengunjung lama langsung mendapat layar putih pada kunjungan berikutnya.
- **Usaha:** S.

---

**P0-4 — Jaringan putus saat loading → menggantung selamanya**

- **Reproduksi:** buka aplikasi, matikan jaringan setelah ~1 detik.
- **Dampak:** progress bar berhenti di 94%, tidak ada pesan, tidak ada tombol coba lagi, tidak ada timeout. Pengunjung menatap layar diam tanpa penjelasan.
- **Penyebab:** `finishLoading()` menunggu `dataReady && !glActive`; kalau `useProgress` tidak pernah selesai karena request menggantung, kondisi itu tidak pernah tercapai. Tidak ada penanganan `onError` `DefaultLoadingManager`.
- **Bukti:** snapshot setelah 12 detik offline masih menampilkan onboarding di atas layar loading 94%.
- **Usaha:** M.

---

**P0-5 — Gerak tidak dibatasi per frame: pemain melompat menembus dunia**

- **Reproduksi:** tahan W, lalu picu hitch (kunci layar, tab ke latar belakang, atau biarkan model besar didecode).
- **Dampak terukur:** jeda frame **2190 ms** → `deltaPos = 4,2 m/s × 2,19 s = 9,2 meter dalam satu langkah tabrakan tunggal`. Hall 1 dalamnya 15 m. Pemicu gerbang lebarnya 5 m: satu langkah 9,2 m bisa **melewatinya sama sekali** (transisi tidak terjadi) atau melemparkan pemain ke seberang ruangan.
- **Terkonfirmasi juga di kondisi biasa:** berjalan lurus dari spawn memindahkan pemain ke Hall 2 dalam **1047 ms**, padahal gerbang berjarak 10,5 m — mustahil pada 4,2 m/s tanpa lompatan frame.
- **Penyebab:** `useFrame((_, delta) => ...)` di `PlayerRig.tsx:256` tidak pernah membatasi `delta`, dan tabrakan dievaluasi sebagai satu langkah diskrit tunggal (`PlayerRig.tsx:496-535`), bukan swept/substep.
- **Kenapa ini penting untuk museum:** perangkat target adalah HP kelas bawah yang mengalami hitch 0,5-2 detik secara rutin, dan pengunjung museum mengunci-membuka layar terus-menerus.
- **Usaha:** S (clamp delta) + M (substep) — sebaiknya keduanya.

---

**P0-6 — Berjalan lurus dari titik masuk melewatkan SELURUH koleksi**

- **Reproduksi:** masuk scene, tahan W, jangan lakukan apa pun lagi.
- **Dampak:** pengunjung melintasi seluruh Hall 1 dan keluar ke Hall 2 **tanpa satu pun artefak masuk jangkauan interaksi.** Perilaku default aplikasi adalah keluar dari pameran.
- **Bukti geometris (diturunkan, bukan dikira):** jalur lurus dari spawn (0, 6) menuju gerbang (0, −7). Artefak terdekat ke jalur itu:
  - `r1-kapak-persegi` di (−4, −0,8): jarak tegak lurus **4,00 m**, radius pemicu **2,70 m** → meleset 1,30 m
  - `r2-surya-stambha` di (3,8, −1,2): jarak **3,80 m**, pemicu **2,88 m** → meleset 0,92 m
  - Semua artefak lain lebih jauh lagi.
- **Bukti terukur:** 5 percobaan berjalan lurus, prompt "Lihat …" bernilai `null` di setiap sampel.
- **Usaha:** S (pilih salah satu: perlebar pemicu untuk artefak dekat sumbu, geser 1-2 artefak ke sumbu, atau tambahkan konfirmasi di gerbang).

## 9. CATATAN TAMBAHAN

1. **Fitur yang tidak pernah bisa diakses pengguna:** `useAmbience` (tidak dipasang), `PottedPlant` (tidak dipasang), progres kunjungan (tidak ada UI), dan 19 artefak tanpa model (tidak dirender, tidak terdaftar di mana pun).
2. **Loading pertama di Slow 3G: ±13,9 menit.** Tidak masuk akal untuk pengunjung museum. Ini harus turun ke bawah 1 menit untuk aset kritis.
3. **Layak dipasang sebagai PWA?** Manifest dan SW sudah benar secara teknis, tetapi karena SW tidak menyimpan apa pun, "install" tidak memberi keuntungan apa pun selain fullscreen — dan mengunduh 40 MB setiap dibuka. **Rekomendasi: perbaiki precache dulu, baru dorong sebagai PWA.**
4. **Pengelolaan konten:** `artifacts.json` + `artifactRepository.ts` sudah dirancang untuk ditukar dengan API tanpa mengubah komponen. Menambah artefak sekarang butuh: edit JSON, taruh `.glb`, dan tambah id di `KNOWN_IDS`. Wajar untuk sekarang.
5. **Wi-Fi museum:** 30 pengunjung serentak × 59 MB pada 20 Mbps = **±12,4 menit** untuk melayani semuanya. Dengan 100 pengunjung, jaringan museum praktis lumpuh. Ini masalah nyata dan harus diselesaikan bersama poin 2.
6. **Tiga hal terpenting sebelum dipakai publik luas:**
   1. **Semua kegagalan harus punya wajah.** WebGL hilang, context hilang, jaringan putus, data lama rusak — keempatnya sekarang layar kosong. Ini P0-1 s/d P0-4.
   2. **Turunkan unduhan awal di bawah 5 MB.** 40 MB sebelum layar pertama membuat aplikasi ini tidak bisa dipakai di luar jaringan kantor.
   3. **Pastikan pengunjung bertemu artefak.** P0-6: perilaku default saat ini adalah melewatkan seluruh koleksi.

## 11. LAMPIRAN — CARA MENGULANG PENGUJIAN INI

Seluruh pengujian runtime dijalankan lewat Chrome headless + Chrome DevTools Protocol, tanpa dependensi baru:

```bash
npm run build
npm run preview -- --port 4173 --host 127.0.0.1
# lalu jalankan skrip driver CDP terhadap http://127.0.0.1:4173/
```

Yang diukur dan bagaimana:

| Besaran | Metode |
|---|---|
| Console | `Runtime.consoleAPICalled` + `Log.entryAdded` + `Runtime.exceptionThrown` |
| Jaringan | `Network.*` + `performance.getEntriesByType('resource')` |
| Kebocoran GPU | Membungkus `create/deleteTexture/Buffer/Program` pada `WebGLRenderingContext` sebelum aplikasi dimuat |
| Jeda frame | Membungkus `requestAnimationFrame` sebelum aplikasi dimuat |
| Kegagalan aset | `Network.setBlockedURLs` |
| Jaringan putus | `Network.emulateNetworkConditions { offline: true }` |
| WebGL hilang | Menimpa `HTMLCanvasElement.prototype.getContext` agar mengembalikan `null` |
| Context lost | `WEBGL_lose_context.loseContext()` |
| `localStorage` rusak | `Page.addScriptToEvaluateOnNewDocument` |
| Emulasi HP | `Emulation.setDeviceMetricsOverride` + `setTouchEmulationEnabled` |

Disarankan menjadikan langkah-langkah ini bagian dari `docs/CHECKLIST-RILIS.md` (Fase F.3).
